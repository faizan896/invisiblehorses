# Milestone 4: common payment lifecycle

Every new HTTP/MCP request uses recipient resolution, deterministic compliance/policy gates, route selection, source reservation and one durable execution operation. New legacy-format wallet requests are translated through the same router and must match the owner's catalog; historical requests retain their fingerprints, IDs and transaction hashes. The CLI binds the payer wallet and optional DataCo demo wallet from private local configuration. Wallet addresses in the example catalog are fictional.

The common statuses are `created`, `recipient_resolved`, `route_selected`, `funds_reserved`, `in_transit`, `settled`, `completed`, `failed`, `returned`, plus approval/denial/rejection/expiry outcomes. Internal test-ledger payments traverse the same stages atomically. Bank settlement precedes recipient availability. Base Sepolia confirmation alone cannot complete a bank-form intent.

- The test ledger and mock bank sources each start with $100 of fictional money, once per configured source/database. Atomic source holds prevent double allocation. The append-only double-entry transfer journal debits/credits integer minor units. Restarting preserves balances; agents cannot reset or seed them.
- USDC uses the actual testnet wallet balance and guarded signer. Signed bytes and hash are saved before broadcasting; RPC ambiguity and restart only replay those bytes. Interrupted preparation is quarantined. One unresolved transaction blocks further signing on that wallet.
- Every execution rechecks current policy, UTC daily allowance, recipient identity, quote validity, requested amount/currency/form and approval cap. Owner approvals expire in 15 minutes. Expired quotes are repriced; automatic replacement cannot exceed the approved source cost. A changed beneficiary requires a new request.
- Only a proven no-outflow/no-FX/no-fee failure permits automatic fallback. New quotes pass all gates again. Unknown outcomes retain the original operation and accounting; they cannot initiate another payment.
- Mock bank rejection returns principal from escrow to the original payer and retains fees. Mock ledger/bank returns are journaled exactly once. USDC returns require cooperation from the original recipient and a matching optional `DEMO_RECIPIENT_PRIVATE_KEY`, plus test ETH for that wallet's gas. A return is not reported until its receipt confirms success. Missing cooperation or a reverted return never invents a refund.
- `POST /owner/payments/:id/return` accepts an empty JSON object with owner authentication. Agents have no reverse/approval/policy-editing MCP tool. Returned keys remain consumed and cannot pay again.

Run `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, then `pnpm start` with the private configuration. MCP accepts full destination-denominated intents, with backward compatibility for legacy wallet requests. The read-only quote and planning endpoints remain read-only.

All ledger/bank balances, ACH, Wise-style payouts, FX and on/off-ramp legs are simulations. Only the fixed Base Sepolia USDC contract can move external test tokens. A configured Wise sandbox provider remains quote-only; no Wise transfer API is called. Modeled USD fees are conservative policy/accounting amounts, not a claim of actual live provider charges.

Validation covers lifecycle stages, settlement versus availability, source/budget reservations, single-use approvals, expiry and repricing, recipient/policy changes, UTC rollover, safe and unsafe fallback, interrupted preparation, timeout after broadcast, old-record migration/idempotency, native revert and return failures, signing serialization, bank closure/returns, and full-intent MCP/owner API boundaries. Live M1 evidence remains in milestone-1.md. No additional live spend or real cooperative return was needed or performed for this milestone.
